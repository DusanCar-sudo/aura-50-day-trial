# `interface` vs `type` in TypeScript

Both describe the shape of a value. The differences that actually matter:

## 1. Declaration merging — the big one
`interface` can be declared twice and the declarations merge. `type` cannot.

```ts
interface User { name: string }
interface User { age: number }
// User = { name: string; age: number }  ✅

type User = { name: string }
type User = { age: number }  // ❌ Duplicate identifier
```

This is why library authors use `interface` for public API surfaces — consumers can augment them (e.g. `declare module 'express' { interface Request { user: User } }`).

## 2. What each can express
`type` is strictly more powerful — it can alias *anything*:

```ts
type ID = string | number;              // union — interface can't
type Pair = [number, number];           // tuple — interface can't
type Handler = (e: Event) => void;      // function type
type Keys = keyof User;                 // mapped/derived types
type PartialUser = Partial<User>;       // utility types
```

`interface` can only describe object/class shapes (plus `extends` and call/construct signatures).

## 3. Extending
Both extend, with different syntax and different failure modes:

```ts
interface A extends B {}          // checked at declaration; error if incompatible
type A = B & { extra: string };   // intersection; silently produces `never` on conflicts
```

That's a real footgun: `interface` catches conflicting members immediately, `type` intersections can collapse to `never` and only blow up later at the use site.

## 4. Performance
Interfaces are lazily evaluated and cached by name — cheaper for the compiler on large codebases. Type aliases (especially deep intersections) get re-evaluated and can slow down big projects.

## 5. Error messages
Interface names show up in errors (`Type 'X' is not assignable to 'User'`); complex type aliases get expanded inline, which is noisier.

## 6. Implements
A class can `implements` either one. No difference.
