## `process.execPath` — what it actually is

`process.execPath` is a **string property** on the `process` object. It holds the **absolute path to the executable that started the current Node.js process** — i.e. the `node` binary itself (or whatever binary embeds Node, e.g. an Electron or `pkg`-bundled app).

```js
console.log(process.execPath);
// /usr/local/bin/node
// C:\Program Files\nodejs\node.exe
```

Key facts:

- **It is a property, not a function.** `process.execPath` — no parentheses, no arguments. Calling `process.execPath(...)` throws `TypeError: process.execPath is not a function`.
- **It is not on `child_process`.** There is no `exec.execPath`. `child_process` has `exec`, `execFile`, `spawn`, `fork` — none of them expose `execPath`.
- **It is read-only in practice** and reflects the *running* binary, not `process.argv[0]` (which is the script path or a symlink-resolved variant depending on how Node was invoked).

## What it's actually for

The canonical use is **re-spawning Node itself** — running a script in a fresh Node process using the exact same interpreter that's running now, rather than trusting `node` on `PATH`:

```js
const { spawn } = require('node:child_process');

// Run another script with the same Node binary
const child = spawn(process.execPath, ['worker.js', '--flag'], {
  stdio: 'inherit',
});

child.on('exit', (code) => console.log('worker exited', code));
```

Why this matters:

1. **PATH independence.** A user's `PATH` may point at a different (older/newer) `node`, or none at all. `process.execPath` guarantees the same runtime.
2. **Bundled/embedded runtimes.** In a `pkg`/SEA/Electron app, `node` may not exist on the machine at all — `process.execPath` is the only correct interpreter path.
3. **Version consistency.** Child processes inherit the parent's Node version, so native addons and syntax features behave identically.
4. **CLI tools** use it to relaunch themselves with different flags (e.g. `--inspect`, `--max-old-space-size`) or to run a worker in a separate process.

## Related properties (often confused)

| Property | Meaning |
|---|---|
| `process.execPath` | Absolute path to the **Node binary** |
| `process.argv[0]` | Path to the executable as invoked (may be relative/symlinked) |
| `process.argv[1]` | Path to the **script** being run |
| `process.cwd()` | Current working directory |
| `process.pid` | PID of the current process |

# First check: `journalctl -u <service> -n 100 --no-pager`

The journal is the only thing that tells you *why* it died. Everything else is guessing.

```bash
journalctl -u myapp.service -n 100 --no-pager -o short-precise
```

Read the last exit before each restart. That single command splits the problem in two:

| What you see | What it means |
|---|---|
| `status=1/FAILURE`, a stack trace, `Error:`, `EADDRINUSE` | **The app is crashing.** Fix the app. Restart policy is irrelevant. |
| `status=203/EXEC` | **ExecStart path/binary is wrong or not executable.** |
| `status=200/CHDIR` | **WorkingDirectory doesn't exist.** |
| `status=217/USER` | **User= doesn't exist.** |
| `status=226/NAMESPACE` | Sandboxing directive (`ProtectSystem=`, `PrivateTmp=`…) blocks a path the app needs. |
| `status=0/SUCCESS` then restart | **The app exits cleanly on its own** — it's a `Type=simple` service whose process forks/daemonizes, or a one-shot script. |
| `start-limit-hit` / `Start request repeated too quickly` | systemd gave up. `systemctl reset-failed` before retrying. |
| Nothing at all, or `Scheduled restart job` | **systemd is killing it**, not the app — see step 2. |

# Second check: is it the app or systemd?

```bash
systemctl show myapp.service -p NRestarts -p ExecMainStatus -p ExecMainCode -p Result
```

- `Result=exit-code` / `signal` → the process died. Back to the journal.
- `Result=timeout` → it's being killed by a timeout, not crashing.
- `Result=success` → it exited 0. The service is misconfigured, not broken.

Then confirm the restart cadence is actually the unit's, not a loop:

```bash
systemctl cat myapp.service | grep -E 'Restart|RestartSec|StartLimit'
```

`Restart=always` + `RestartSec=30` means a 30-second cycle is *expected behaviour* for a service that keeps dying. The 30s is the symptom's rhythm, not the cause. If `RestartSec` is 30 and you see restarts every 30s, the unit is doing exactly what it was told — the bug is upstream.

# Third check: the three things that cause this most often

1. **Environment is empty.** systemd does not source `.bashrc`, `.profile`, or `.env`. A service that works in your terminal and dies under systemd is almost always this — `PATH`, `NODE_ENV`, API keys, `HOME`. This repo's own `aura-telegram-bot.service` is a live example: it sets `Environment=NODE_ENV=production` but nothing else, and `ExecStart=/usr/bin/node` is an absolute path precisely because `PATH` isn't inherited. If that unit were failing, `node: not found` or a missing API key would be the first thing in the journal.
2. **Port already in use.** `EADDRINUSE` on a port a previous instance or another unit holds. Check with `ss -ltnp | grep <port>`.
3. **A dependency isn't up yet.** `After=network.target` is not "the network works" — it's "the network unit was reached". For anything that needs DNS or a real connection, use `After=network-online.target` + `Wants=network-online.target`.

# What not to do

Don't start by editing `Restart=` or raising `RestartSec`. That hides the crash and turns a 30-second loop into a 5-minute loop. The restart policy is working correctly — it's faithfully restarting a service that keeps dying.

**One-line answer:** `journalctl -u <service> -n 100 --no-pager` and read the exit status before each restart. That tells you whether the app is crashing, the unit is misconfigured, or systemd is killing it — and those three have completely different fixes.

  const added = new Set<string>();
  const removed = new Set<string>();
  const modified = [];

  // Merge keys from both objects
  const allKeys = new Set([...Object.keys(a), ...Object.keys(b)]);

    if (a.hasOwnProperty(key)) added.add(key);
    if (b.hasOwnProperty(key)) removed.add(key);

    }
  };

}

const generateApiKey(): ApiKey {
  // Step 1: Generate a secure random prefix (32 hex chars)
  const prefix = uuidv4().slice(0, 32).toString(16);

  // Step 2: Build key string
  const rawKey = `${prefix}-${Math.trunc(Date.now() * 1000000).toString(36)}`;

  // Step 3: Compute SHA-256 of the key + checksum hash
  const keyBytes = Buffer.from(rawKey, 'hex');

## 1. Overview – Builder Pattern (Unified)
The builder pattern separates construction logic from the final object, making it ideal for complex objects. We’ll implement it in TypeScript, Python, and Go so you can compare approaches without needing extra tooling.

### Common Steps
1. **Define an abstract `Product` interface** (or class) with all properties.
2. **Create a concrete builder class** that holds the current state and provides methods to set each property.
3. **Build the object incrementally** via a fluent API or chainable methods.
4. **Validate & finalize** before returning the constructed instance.

---

## 2. TypeScript Example
```typescript
interface Product {
  id: number;
  name: string;
  price: number;
}

class Builder<T> {
  private properties = {};

  set propertyName(value: T): Builder<T> {
    this.properties[propertyName] = value;
    return this; // chainable
  }

  build(): Product {
    const product: Product = {};
    for (const [key, val] of Object.entries(this.properties)) {
      product[key] = val;
    }
    return product;
  }
}

// Usage:
const builder = new Builder<Product>();
builder.setName("Widget")
  .setPrice(19.99)
  .build();
console.log(builder); // { id: 1, name: "Widget", price: 19.99 }
```

type Product struct {

type Builder struct {
	properties map[string]interface{}
}

func NewBuilder() *Builder {
	return &Builder{properties: make(map[string]interface{})}
}

func (b *Builder) SetProperty(key string, value interface{}) {
	b.properties[key] = value
}

func (b *Builder) Build() Product {
	product := Product{}
	for k, v := range b.properties {
		switch v := v.(type) {
		case int:

		case float64:
