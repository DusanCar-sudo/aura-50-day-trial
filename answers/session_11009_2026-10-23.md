## `process.execPath`

It's a string property that gives the **absolute path to the executable that started the current Node.js process** — i.e. the `node` binary itself, not your script.

```js
console.log(process.execPath);
// Linux:   /usr/bin/node
// macOS:   /usr/local/bin/node
// Windows: C:\Program Files\nodejs\node.exe
```

### What it's for

**1. Spawning a child Node process with the same runtime**
The canonical use. If you need to run another script in a child process, you don't want to hardcode `"node"` (it may not be on `PATH`, or a different version may be picked up):

```js
const { spawn } = require('node:child_process');

spawn(process.execPath, ['worker.js', '--flag'], { stdio: 'inherit' });
```

This guarantees the child runs on the *exact same* Node binary — same version, same flags, same install — which matters for native addons (ABI compatibility) and for tools that re-exec themselves.

**2. Re-executing the current process**
Used by CLIs that need to restart themselves with different flags (e.g. after enabling `--inspect`, or to relaunch with `--max-old-space-size`):

```js
spawn(process.execPath, [...process.execArgv, ...process.argv.slice(1)], { stdio: 'inherit' });
```

Note the pairing with `process.execArgv` (the Node-level flags like `--inspect`) and `process.argv` (script + args).

**3. Locating the Node installation**
From the path you can derive the install root — useful for finding bundled resources, `npm`, or the `node_modules` global prefix:

```js
const path = require('node:path');
const nodeDir = path.dirname(process.execPath); // /usr/bin
```

**4. Packaging / bundling**
Tools like `pkg` or `nexe` (which embed Node into a single binary) set `process.execPath` to the *packaged* executable, so code that spawns `process.execPath` keeps working after packaging. That's a deliberate design property: it always points at "the thing that is running me," whatever that is.

### What it is *not*

- **Not** the script path — that's `process.argv[1]` (or `__filename` / `import.meta.url`).
- **Not** the current working directory — that's `process.cwd()`.
- **Not** the directory containing your code — that's `__dirname`.
- **Not** writable — it's read-only.

### One caveat

`process.execPath` is resolved at startup and is not affected by later `process.chdir()`. But it *can* be a symlink path (e.g. `/usr/local/bin/node` → `../Cellar/node/...` on Homebrew), so if you need the real binary, resolve it with `fs.realpathSync(process.execPath)`.
