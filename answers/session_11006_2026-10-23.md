**`process.execPath`** returns the **absolute path to the executable file that started the current Node.js instance**.

- It points directly at the binary (e.g., `/usr/bin/node`, `C:\Program Files\node\node.exe`) rather than any script or module you may be running.
- Because it’s a property of the global `process` object, you can use it anywhere in your code to discover where Node was launched from.

**Typical uses**

| Use case | Why `execPath` is handy |
|----------|------------------------|
| **Determining script location** – If you need to know which executable started the process (e.g., a wrapper that launches Node), `process.execPath` gives you the exact path without having to parse command‑line arguments. |
| **Logging / diagnostics** – Include the full binary path in logs or error messages so users can see exactly what version of Node was used (`console.log('Node executable:', process.execPath)`). |
| **Self‑modifying scripts** – A script that needs to replace itself (e.g., a hot‑reload utility) can write its new code into the same file referenced by `process.execPath`. |
| **Cross‑platform checks** – On Windows you might get something like `C:\Users\me\AppData\Local\nodejs\node.exe`; on Unix it’s `/usr/bin/node` or similar. Knowing this lets your script adapt behavior accordingly (e.g., different shebang lines). |

In short, `process.execPath` is a simple way to read the **path of the Node executable** that launched the current process, useful for introspection and debugging but not for locating user‑written scripts (`__filename`/`__dirname` are better suited for those purposes).

**How episodeStore namespaces episodes for different projects**

The namespace is built from two pieces of information that uniquely identify a project:

| Piece | Where it comes from | How it’s used |
|-------|--------------------|---------------|
| **Project name / identifier** | The directory inside `projects/` (e.g., `gpu-dashboard`, `lesson-prep`) or the slug stored in the episode file (`projectHash`). | It becomes the first segment of the namespace, separated by a colon. |
| **Episode‑specific hash** | A SHA‑256 digest computed from the episode’s raw content (title + body). This hash is called `projectHash` and guarantees that two episodes with identical text will have exactly the same identifier even if they live in different projects. | It forms the second segment of the namespace, also separated by a colon (`:`). |

**Namespace format**

```
<project‑identifier>:<projectHash>
```

*Example*

- **Project**: `gpu-dashboard` (the directory under `/mnt/bigdata/aura/projects/gpu-dashboard`)
- **Episode file content**:  

  ```markdown
  # Episode Title – How to run a local model demo
  …body…
  ```

- **Computed hash** (example): `a1b2c3d4e5f6…`  
  *(the exact SHA‑256 value depends on the episode’s text)*

Resulting namespace:

```
gpu-dashboard:a1b2c3d4e5f6…
```

So an episode stored in `/mnt/bigdata/aura/projects/gpu-dashboard/episode-123.md` would be referenced as **`gpu-dashboard:a1b2c3…`**. The same hash is used for any other project that happens to have the exact same markdown text, guaranteeing uniqueness across projects while still allowing a human‑readable identifier (`gpu-dashboard`) to tell apart different codebases.

### Implementation of `projectHash`

The function responsible for generating this unique identifier lives in **`episodeStore/episodeStore.ts`**:

```ts
export const projectHash = (content: string): string => {
  // Compute a SHA‑256 digest of the episode’s raw content.
  return crypto.createHash('sha256')
    .update(content, 'utf8')
    .digest('hex');
};
```

* What it does  
  * Takes the **entire markdown/text** of an episode (title + body).  
  * Feeds that string into Node’s `crypto` module with algorithm `'sha256'`.  
  * Returns the hexadecimal digest (`hex`).  

* Why this works for namespace uniqueness  
  * SHA‑256 is cryptographically strong and deterministic – identical input always yields the same hash.  
  * Even a tiny change in wording or formatting produces an entirely different hash, so two episodes with only minor differences will have distinct namespaces.  
  * The function runs **once per episode** (when the episode file is first read), producing a stable identifier that can be stored alongside the episode’s metadata.

* Where else it appears  

| File | Role |
|------|------|
| `episodeStore/episode.ts` | Provides helper methods (`getEpisode`, `saveEpisode`) that use the namespace when reading/writing episodes. |
| `episodeStore/index.ts` | Exports both `projectHash` and other utilities, making the hash function available to callers (e.g., in batch scripts). |
